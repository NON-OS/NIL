# Changelog

All notable changes to Nil, the task app made by NØNOS, are listed here, newest first. Versions up to 3.0.0 were released under the NØNOS name.

## Unreleased

### Breaking changes

- `APP_URL` is required. The server refuses to start without it. Wallet sign-in messages and the origin check use it, plus `ALLOWED_ORIGINS`, and never the Host, Origin or X-Forwarded-Host headers. Plain http is accepted only for localhost and .onion addresses. With `npm run dev`, set `APP_URL=http://localhost:5173`. Onion-only servers set it to their .onion address: [docs/tor.md](docs/tor.md) shows the two-step first start.
- `NOX_RPC_URL` is required on a server people reach over the network. There is no public default any more, because a public node sees every address the server looks up. Set your own node, a provider you trust, or `off`. A server whose `APP_URL` is a localhost address still falls back to a public node, with a startup warning.
- `TRUST_PROXY` no longer accepts `true`. Give the proxy's address or subnet (`uniquelocal` for Caddy in the same Compose project, `loopback` for a proxy on the same machine) or a hop count. A value it can't use is ignored with a warning.
- `docker-compose.tor.yml` removes Nil's published port, so an onion-only server no longer answers on its normal IP address.
- Hosted: Lighthouse in `docker-compose.chain.yml` now serves its beacon API on the internal chain network, for Nil's verifier; current Lighthouse releases serve the light-client endpoints by default.

### Security and privacy

- A phishing site could ask for a sign-in message naming its own domain when `APP_URL` was empty, pass the wallet's domain check and relay the signature to sign in as someone else. Requiring `APP_URL` closes this.
- Guests no longer hear about tasks they can't open. Notifications, mentions, watchers, vote notices, presence and the timesheet export all check who can open the task. Whoever loses access to a task (made private, reassigned, moved out of a guest's projects, a project unshared or deleted) also loses their watch, its notifications and its My Day entry.
- Anonymous ballots are held until the hour they arrived in has ended, then counted together in random order and stored with the hour only, so neither the live count nor the database shows when a ballot came in. Voting keys are registered when a member first unlocks their keys or clicks **Join anonymous votes**, never together with a ballot, and only their owner sees them. The audit file lists ballots by nullifier with hour stamps, and existing ballot and voter-tree times are rounded to the hour (migration 020).
- Signing out closes the live connection that session opened, and live connections close once their session expires or is revoked. Over HTTPS only the `__Host-` session cookie is read, so a cookie planted by a sibling subdomain signs nobody in.
- Sign-in and bounty-application challenges are no longer kept in a shared table that one IPv6 /48 could fill until nobody could sign in. Each challenge comes back to the server in the token the client holds, with an HMAC over its message, the client's network and its expiry, works once, and only from the network that asked for it. Rate limits by address count an IPv6 /64 as one client and also cap each /56 (four times as much) and /48 (sixteen times), and a smart wallet's on-chain check only follows a challenge given to that network.
- One admin can no longer reset an owner's sign-in alone. Only an owner can change the role of, remove or delete another admin. Admins who lost the role within `SIGNIN_OWNER_RESET_WAIT_HOURS` (72) still count toward needing a second admin, and only an admin of at least that long whose own sign-in wasn't reset meanwhile can approve. With nobody to approve, the reset waits that long before the admin who asked can make the link, and the owner and the other admins are told, in the app and by push, so they can cancel it.
- An admin's invite links and sign-in resets stop when they do. Demoting an admin or removing their access revokes the invite links they made and closes the unused resets they asked for or approved; removing anyone's access revokes their links. When used, an admin invite needs its maker to still be an admin, and a reset link its asker and approver.
- Sign-in resets refuse agents, which never sign in. Deleting an agent ends its sessions and live connections, the live connection's heartbeat drops anyone whose access was removed, and an agent account only takes its own agent key.
- A borrowed session can't leave a way back in. Linking another wallet and making an access key need a fresh signature from a wallet already linked to the account, good for `SIGNIN_CONFIRM_MINUTES` (5) in that session. Access keys can't be made without an expiry and last at most `ACCESS_KEY_MAX_DAYS` (365), which also ends older keys at that age. A sign-in reset revokes the person's access keys, and **Sign out on all devices** offers to.
- One stack of NOX keeps one person in through the token-holder door. Each wallet's holdings count for one account at a time, and Nil remembers which, even after the wallet is unlinked: for the grace period after, they count for nobody else and the wallet can't be used to join. The regular checks read every door member at the same block, and only they can see someone holding enough again. That lets a locked-out member back in once it has lasted `HOLDER_RECHECK_HOURS`, and ends the shortfall, so the next one gets a fresh grace period, only after a whole grace period of holding. A sign-in can find someone below but never let them off. Locked-out members' access keys stop working until they're back. Holdings are read the way vote snapshots are: at the newest final block, named by hash, with a staking or pass contract that reverts counting as nothing staked and no passes instead of failing every join and check, while a node that can't be reached, or an answer that can't be verified, still changes nobody's place.
- Holders joining through the door at the same moment can't take more seats than the plan has: the door, plan and seat checks run again inside the join's transaction. The re-check each join asks for runs one pass at a time, and any number of joins during a pass share one more.
- Migration 033 adds what these need: when each admin got and lost the role, the wait on an owner's reset, the session's last wallet confirmation and the holder door's wallet records, and clears any session or wallet an agent was given.
- Private payout balances are read from the Ethereum node one address at a time, at random moments within `STEALTH_BALANCE_SPREAD_SECONDS`, with another payee's address mixed in, and listing payouts no longer calls the node. Vote snapshots read wallets in a shuffled order, a few at a time.
- A private payout's throwaway key stays in the payer's browser. The browser used to send it to the server, which worked out the one-time address from it. That let the server work out how each payout's key relates to the contributor's spending key, so one payout key they exported with **Key** would have given away the spending key and every payout sent to it. Now the browser works out the address and sends only the address, the throwaway public key and the view tag. The server refuses an address or throwaway key it has seen before and any sign-in wallet, and the contributor's browser checks the address before moving a payout. A tab opened before this release has to reload before it can pay privately.
- Wiping the workspace, purging, erasing a person or task, deleting a comment and sealing a task now also clear SQLite's write-ahead log, so deleted text doesn't linger in `nonos.db-wal`.
- Backups are checked before they're kept. `deploy/backup.sh`, new, backs up a self-hosted server while it runs: a `VACUUM INTO` copy of the database made inside Nil's container and checked there with `PRAGMA integrity_check` and `foreign_key_check`, then archived with the keys and uploads, the archive's database hashed against the copy that was checked, optionally encrypted with age (`--age-recipient`), with old archives pruned. It replaces the script that [docs/deploy.md](docs/deploy.md#10-backups) had you copy, which didn't check the copy, briefly copied the live database files out and left a plaintext copy in `/data` when it failed halfway. The guide now shows how to check an archive and restore it on both kinds of server. Hosted backups run the same checks inside each workspace, and a database that fails them fails the backup with an alert.
- A capsule that decrypted fine was trusted as it was. A doctored one could bring rows pointing at nothing, triggers of its own, or a table whose columns didn't line up with this server's, and a failure while copying files or keys after the rows went in left a restore half done. A restore now checks the capsule's database (integrity, no code Nil didn't write, the exact schema once upgraded, foreign keys, a workspace with an owner) and its keys (an Ed25519 signing key, the one its receipts were signed with) before it changes anything, refuses with the reason, and puts the keys in place only once the rows have gone in. It also rebuilds the search index once instead of once per comment.
- The zero-state sweep reached tasks, comments and history but not everything around them. Sent reminders kept their notes, dead share links, sign-in reset links and API keys stayed for good, bounty payments started but never sent kept who was paying whom and how much, the sign-in audit trail and agents' webhook delivery log ignored the task history policy, and each copy of the database taken before an upgrade kept everything erased since for as long as it existed. Sent reminders now go at once, dead links, keys and payments after `EXPIRED_DAYS` (30), the audit trail and the delivery log with the history policy, and upgrade copies after `UPGRADE_COPY_DAYS` (7) or the shortest policy. A weighted vote keeps the power of members who didn't vote for `VOTE_POWER_DAYS` (90) after it closes. A capsule export or restore cut off by a crash no longer leaves a plaintext copy of the database in the data folder.
- Bounty totals leave out private tasks the viewer can't open, admins included.
- The AI draft and deck dialogs say that the text passes through the Nil server on its way to Anthropic. The README lists what the server still knows about a private task.
- `image-size`, which pptxgenjs declares but never loads, is pinned to 2.0.4, past its denial-of-service fixes.
- Anyone can check that a server sends exactly the web app of a release. The build is byte for byte the same on any machine, `npm run release:manifest` writes a manifest of every file with its SHA-256 and the release hash that stands for all of them, and `npm run verify:server -- <address>` compares a running server with your own build or a published manifest: every file, the routes the app opens on, and the Content-Security-Policy. See [docs/verify-a-server.md](docs/verify-a-server.md).
- Private tasks warn when the server sends an older version than this browser has already opened, as docs do. Every save seals the task's words under the next revision number, which the writer's signature covers, so an old version can't be passed off as new. Tasks sealed before this open as revision 0.
- Private tasks and docs now sign who they're for and which key protects them. A server, or an account it holds, could get a private task's key by listing itself as the assignee, have a doc shared with one person sealed to the whole team by calling it a team doc, or seal a task or doc under a key of its own, signed by a user nobody could see, and read the next edit. Now each private task's words are signed with their creator and assignee and a hash of the task key, and each doc version with its audience, its readers and a hash of the doc key, together with the time. A browser opens them only when the signer is one of those readers, the key it unwrapped has the signed hash and, for a task, the people it shows are among those signed. Keys are handed over only to signed readers, and team docs only reach newcomers when the version is signed for the team. An assignee who hands a task on is named, and the next edit moves the task to a key they never saw.
- Comments on private tasks are signed for their own id and an edit number, so the server can't show a comment from before its last edit, swap two comments or bring back a deleted one unnoticed. The browser picks a new comment's id, and `POST /api/tasks/:id/comments` takes it as `id` for an encrypted comment. A comment signed by someone other than its author, as happens when a task turns private, says who signed it. Files on private tasks have their name, type, size and SHA-256 signed by whoever attached them.
- Confirming a teammate's key pins exactly the key on screen, and only if the server still lists it, so a key swapped in while fingerprints are being compared isn't the one confirmed. The Docs notice and Teammates' keys also show keys of deactivated members and of people the workspace doesn't list, and a key seen for the first time counts for signatures only while it's listed for an active member.
- After a teammate resets their keys and you confirm the new one, what they signed with the old one before the reset still opens, marked as signed with their earlier key, instead of locking for good.
- A server that lists no keys and no wallet copies for someone can't quietly move them onto new keys any more. If the browser has seen them hold keys in the workspace, unlocking stops with "Your keys seem to be missing from the server" and offers the recovery kit, or starting over as a choice.
- Private tasks, docs, comments and files saved before these signatures open as before, marked as the older format. Nil never shares them on its own, and the next save, or editing a comment, signs them in the new format.
- The ballot circuit's phase 2 setup can now run as a real ceremony between people who don't trust each other: `npm run ceremony:start`, `ceremony:contribute` and `ceremony:finish`, with a beacon block announced in advance and the whole chain verified before anything is installed. [circuits/CEREMONY.md](circuits/CEREMONY.md) is the guide for the coordinator and the contributors.
- The public bounty form checks the server's message before the wallet signs it, as sign-in and ballots already did. A dishonest server could have handed a member their own unlock message as a bounty application and opened their keys with the signature. Every message the server writes now goes through the same check, and the hosted sign-up page makes it too.
- Pins and the version records that catch rollbacks stay with the site, workspace key and account the keys were unlocked for. Before, a reconnect could bring a bootstrap with another workspace key while the keys stayed unlocked, and the browser started an empty set of pins that accepted a key the server made for a teammate already confirmed. Now a bootstrap that names a different site, workspace key or account locks the keys and says so, and the tab won't unlock them again until it reloads. At sign-in, a browser that holds pins for another workspace or account but none for this one warns about it.
- Signing out forgets the private tasks, comments and files the tab opened, as locking does. Their words used to stay in memory and show again to whoever signed in next in that tab.
- A private task this tab already opened warns when the server goes back to it after a newer version, like any other older version. The tab's memory of the old version used to skip the check.
- A recovery kit asking for more than 4 times the memory or 8 times the work of the scrypt cost Nil writes is refused, so a doctored kit can't stall the tab.
- A chain reorganisation that moved a Nil Pro payment to another place in its block left it confirming forever, so its invoice could neither settle, expire nor be cancelled, and the transfer could be counted a second time. The payment now moves with the transfer.
- One empty answer from the Ethereum node for a Nil Pro payment's receipt, even after its block was final, dropped the payment for good: the treasury scan never reads a final block twice, and pasting the hash again did nothing. Such a payment now stops counting but is looked for again on every run for `PLAN_LATE_DAYS`, pasting its hash again looks once more, and one receipt the node refuses no longer stops the other payments from being checked.
- Without `PLAN_INVOICE_SLOT`, pasting a transaction hash under a Nil Pro invoice let a workspace claim another workspace's payment to the same treasury whenever its suffix matched. A pasted transaction now pays only that invoice, and an amount Nil didn't ask for counts only when it came from a wallet linked to someone in the workspace.
- A transfer short by exactly NOX's transfer fee counted as paid in full even when the token kept no fee on it, a fee reading of up to 100% was believed (so a misread could let a zero-value transfer pay an invoice), and the treasury scan used today's fee instead of the fee in the transfer's block. Such a payment now counts only when the same transaction shows a Transfer of that fee from the same sender, readings above `NOX_MAX_TRANSFER_FEE_BPS` (300, NOX's 3%) turn fee matching off with a warning to the operator, and the fee is read at the payment's own block.
- A staking or Zero-State Pass contract that reverted blocked every Nil Pro quote and invoice with an error. A reverted call now counts as no stake and no pass, the rule vote snapshots already follow, and when no token at all can be priced the invoice is refused with a 409 instead of a server error.
- Holding a Zero-State Pass for one block gave a workspace about 7 days of Nil Pro with no seat cap, again and again: opening the price preview recorded the pass, and the grace period ran on after the next check found it gone. The pass and staker checks now run at random moments between half of `PLAN_PERK_CHECK_HOURS` and all of it after the last one. A pass gives Pro only once the checks have kept finding it for `PLAN_PERK_CHECK_HOURS`, the price preview and invoices never grant or extend it, and Pro by pass ends at the first check without one, with no grace period and no uncapped seats. The staker discount follows the same rule per tier and per admin, and needs the stake to be there when the invoice is made too.
- A bounty's amount and token could change after a payment was cancelled while still watched, so 1 NOX landing later could mark a 1,000,000 USDC bounty paid, and what a bounty had received added up units across tokens. The bounty is now fixed while any payment for it is pending, confirmed, or cancelled but still watched, and only payments in the bounty's own token count toward it.
- Resetting encryption keys left private payouts on at the old payout keys, so new bounties went to one-time addresses the person could no longer open. A reset now switches private payouts off; switching them on again uses the new keys.
- The voting power snapshot read wallets by block number at the head, so a reorg during the snapshot could mix two versions of that block. It now reads at the newest finalized block (or `NOX_FINALITY_DEPTH` under the head on a node without the tag) and names it by hash in every call (EIP-1898).
- Nil Pro billing and bounty payments can no longer wait forever for a person. With the Ethereum node down, a named transaction that never showed up is given up on after `NOX_MISSING_TX_HOURS` and a payment out of its block after `PLAN_LATE_DAYS`, so invoices expire on time. A reconciliation reads the treasury's recent transfers again every `PLAN_RECONCILE_MINUTES` (over `PLAN_RECONCILE_BLOCKS` blocks) and looks up payments given up on in the last `PLAN_RECONCILE_DAYS`, so a missed or late transfer is still counted, as credit if its invoice closed. A restart halfway through any step picks up where it was, including an invoice whose payment was counted but not yet settled. A billing watchdog tells owners and admins in the app, the server log and `/healthz` (which hosted Nil turns into an operator alert) about anything unsettled `PAYMENT_STALL_HOURS` past its normal time. [docs/nox-and-nil-pro.md](docs/nox-and-nil-pro.md#nothing-waits-for-a-person) lists the guarantees.
- A task made private no longer leaves its words with agents. Runs still going on it stop, the logs and summaries of runs on it are erased, steps in other runs that changed it lose their details, its approval cards are deleted, its audit entries lose their arguments, and replies stored for `Idempotency-Key` stop quoting it. A stored reply is never replayed to a key that can no longer see its task. Reads that bring back tasks are logged as which tasks and how many, not their words. Erasing a task does the same at once, decided approval cards and stored replies follow the retention settings, and changing those settings applies them right away. The agent data sweep now clears the write-ahead log too (migration 031).
- Uploads are checked (the task, the file's headers, its declared size and the uploader's quota) before any of the body is read, then streamed to disk instead of held in memory. Each person can attach `UPLOADS_PER_HOUR` files an hour (120) and keep `UPLOAD_QUOTA_PER_MEMBER_MB` (2048), a guest `UPLOAD_QUOTA_PER_GUEST_MB` (100), and the workspace `UPLOAD_QUOTA_MB` (20480, or 768 in memory-only mode). A staged copy for sealing or opening up a task can't be larger than the file encrypted.
- Outsiders can no longer bury or lock a public bounty. Only applications still waiting count toward the cap (`BOUNTY_MAX_PENDING_APPLICATIONS`, 100), a bounty takes at most `BOUNTY_APPLICATIONS_PER_HOUR` new ones an hour (20), and the per-wallet limit is now `BOUNTY_APPLICATIONS_PER_WALLET` (5). Admins can delete an application and stop a listed bounty taking new ones, and applications for one bounty add up in one unread notification.
- Line breaks in an applicant's name, a task title or the workspace name can no longer add lines to the message a bounty applicant signs.
- A comment's words leave notifications, people's and agents', when it's deleted or erased by the retention policy, and an edit updates them. Agent briefings lose a quoted comment the same way.
- The @mention parser no longer slows down on long runs of dots or dashes.
- CSV exports quote every cell and put an apostrophe before a formula character that follows a `;`, tab or comma as well as one at the start, so spreadsheets that split on `;` or tabs don't run it.
- Hosted Nil's images are now `localhost/nonos/nil`, `localhost/nonos/nil-cloud` and `localhost/nonos/nil-caddy`, and nothing on the server pulls them. The old names, `nonos/nil` and `nonos/nil-cloud`, point at a Docker Hub account NØNOS doesn't own. `CLOUD_IMAGE_PULL` defaults to `never`, the compose files say `pull_policy: never`, the deploy scripts pass `--pull never` and check that the version they would fall back to is still on the server, and a restore runs the image its backup names only if it is ours and already there. `install.sh` moves existing servers to the new names.
- One network can no longer close hosted sign-ups. Limits count an IPv4 address or an IPv6 /56 as one network and a /24 or /48 as one block, per day and per hour, with no budget shared by everyone. Wallet challenges are limited the same way before they are issued, and are sealed tokens the server doesn't keep, so a flood can't push anyone else's out. Past `CLOUD_SIGNUPS_PER_DAY`, or near capacity, a sign-up waits for the operator (`cli.js requests`, `approve`, `reject`). A claimed workspace whose data hasn't changed in `CLOUD_IDLE_DAYS` is paused with a notice and deleted `CLOUD_IDLE_NOTICE_DAYS` later unless its owner asks for it back. The hosting guide recommends wildcard TLS for a public launch.
- Each hosted workspace gets its plan's disk as its upload quota (`UPLOAD_QUOTA_MB`), and one that still grows past `CLOUD_DISK_SUSPEND_PERCENT` (120) of it is suspended with a notice and a critical alert.
- No uid is shared between a container and an account on the host. Each hosted workspace runs as its own uid from 200000 up, and a helper hands its volume to that uid. `provision.sh` creates the deploy user as uid 1500, and `--move-deploy-uid` moves an existing one off 1000. Unattended upgrades now include Docker's own repository.
- `provision.sh` warns about every account other than the deploy user on uid 1000, the control plane's uid inside its container, not only about the deploy user. On OVHcloud that is the installer's `ubuntu` user, with passwordless sudo. `provision.sh --remove-user ubuntu` removes it, its home and `/etc/sudoers.d/90-cloud-init-users`, as the hosting guide did by hand. It runs only from a session that logged in as the deploy user, asks first, and refuses while anything still runs as the account it would remove.
- A restore brings the backup key over SSH into the control plane's memory-only `/tmp` instead of copying it to the host. The control plane, Caddy and the single-mode app can't swap, and `provision.sh` sets up no swap unless asked and warns about swap that isn't encrypted.
- The hosting guide no longer claims that a write-only S3 key keeps a compromised server from destroying its backups. It asks for versioning and Object Lock in compliance mode on the bucket, or snapshots on the Storage Box, and the control plane alerts at startup when the bucket lacks either.
- Every base image is pinned by digest (Node, Caddy and its builder, Debian for Tor, the Dockerfile frontend) and the Caddy DNS module by version. `release.sh` builds from a `git archive` of the commit, so an untracked file can't ship and break the byte-for-byte check. The Tor container runs read-only, with `no-new-privileges` and only the capabilities it needs.
- A Caddy build with a DNS module stops when the Caddy it made isn't the one the images pin. A module that needs a newer Caddy (`caddy-dns/hetzner/v2@v2.0.1` pulls in 2.11.2) used to raise it without a word while the image was still tagged 2.10.2. `release.sh` also checks the version inside the image it tagged.
- Backups, upgrades, rollbacks, restores and first starts of a hosted workspace take a lock in the control database, so a backup never reads a volume halfway through an upgrade. A restarted control plane marks the sign-ups it was provisioning as failed and alerts, and reports anything else left stuck every hour.
- The service worker keeps a file only if its SHA-256 matches the build's own list in `build.json`, fetched fresh on every page load, and drops what no longer matches, so a file changed once on the way doesn't stay for the whole release. A hosted workspace's notice that it is paused or being deleted is shown instead of the stored app.
- `cli.js restore-drill` restores a backup into a throwaway workspace nobody can reach and removes it. The drill the guide described before put a live copy of a customer's workspace online.
- Push notifications are off in hosted workspaces, which have no route to the push services, and [docs/tor.md](docs/tor.md) lists the push services among an onion server's outgoing requests.
- Invoice slots come from a counter that only goes up, so a slot is never handed out twice, and running out of them raises an alert.
- A free workspace could fill the disk every hosted workspace shares with docs alone, since only attachments counted toward its quota: about 30 MB a second from one browser, checked only every 15 minutes. `UPLOAD_QUOTA_MB` now counts the database too, and once it's full new writes get a 413 while reading, deleting and exporting keep working. Docs saved and comments written are limited to `CONTENT_WRITES_PER_MINUTE` (120) per person. Each hosted workspace takes a capsule no larger than its plan (`MAX_CAPSULE_MB`), and a restore needs free disk for twice the capsule. Hosted sign-ups pause by themselves below `CLOUD_SIGNUP_MIN_FREE_DISK_PERCENT` (10) of free disk, with a notice on the page and a critical alert.
- A wallet that joined a member and voted in the app while its ballot from a public vote's page was being read could count twice. Who the wallet belongs to is now asked again in the same transaction as the outside ballot.
- Read-only access keys and read-only agents can no longer follow tasks or mark their inbox read. Both change something, which a read-only key promises not to do.
- Running `provision.sh` again no longer takes the Ethereum node down by handing its engine API secret to the deploy user. Docker waits for the backup share at boot, and the control plane sees the share even when it mounts late.

### Verified chain reads

- Nil's verifier, a new and optional service run once per server (`npm run verifier`, or the `verifier` service in the Compose files): a light client built on Helios 0.12.0 that checks the Ethereum node's answers against the chain the beacon sync committee signed. It proves receipts, logs, blocks, `eth_call`, balances and nonces, relays sending, gas estimates and the pending nonce unproven, and refuses everything else. Each answer comes back sealed with a key it shares with the app.
- `NOX_VERIFIER_MODE` chooses what the server does with it. `off`, the default, changes nothing. `shadow` keeps acting on the node's answers as before and checks each one through the verifier (`NOX_VERIFIER_URL`) on the side: an answer the verifier proves false shows admins a notice for a day, writes an error line and, on hosted servers, raises a critical `workspace.chain_mismatch` alert from the workspace's `/healthz`; one it can't check is only logged, and nothing waits. Hosted servers start in shadow mode (`CLOUD_VERIFIER_MODE`, `CLOUD_VERIFIER_URL`, a second Caddy relay on `CLOUD_VERIFIER_RELAY_PORT`), and run without a verifier, saying so, until `VERIFIER_KEY` is set.
- With `NOX_VERIFIER_MODE=enforce`, the server acts only on proven answers. Bounty payments and Nil Pro invoices are credited only from proven receipts, logs and finalized blocks; vote snapshots, the holder door and smart-wallet sign-in work only on proven balances and calls. When an answer can't be verified, nothing is counted or refused on it: payments wait, votes don't open, nobody joins or is turned away, and admins see a notice saying why on Settings → Plan, Bounties and Votes. A node caught in a false answer stays on that notice for `NOX_VERIFY_MISMATCH_HOURS`.
- A lying node can still leave a log out or say a transaction doesn't exist, so in enforce mode it can hide or hold back a payment but can't fake one. In enforce mode a bounty payment is therefore never failed for a missing transaction; an admin cancels it. A Nil Pro transaction is still given up on after `NOX_MISSING_TX_HOURS`, which only lets its invoice expire, and the reconciliation counts it if it turns up. Blocks older than about 27 hours (EIP-2935) can't be proven, so such a payment waits with a note.
- The verifier refuses a checkpoint older than `VERIFIER_CHECKPOINT_MAX_AGE_DAYS` (14 at most), checking the checkpoint's header itself since Helios's own check is off by default, and keeps the newest checkpoint it reaches for the next start. Helios is unaudited.
- `npm run verifier:mainnet-check` runs it against mainnet with a proxy that tampers with the node's answers, and shows real receipts and balances proven and tampered ones refused.
- `/healthz` shows `chain.verification`.
- One ballot could count two or three times. Proof checkers read numbers with BigInt, so a nullifier with a zero in front verified like the plain one while the server told them apart, and an admin could replay proofs from the audit file that way. Every public signal, proof coordinate, curve point and voting key now has to be plain decimal below its field's size, and a recount compares nullifiers as numbers. The same trick let a member register a copy of someone's voting key as a second seat in every census, and spend a slot of anonymous AI requests twice; their check follows the same rule now. Migration 035 drops held ballots, ballots of open votes and voting keys written any other way.
- A dishonest server could choose an encrypted vote's key by dealing all three trustee seats itself. Trustees now sign their commitment and their dealing with their pinned signing key, voters and trustees check those signatures against their own pins before encrypting or decrypting, and each trustee checks that the dealing shown for its seat is its own. Encrypted votes set up before this carry no signatures, so browsers won't vote in them: start those again.
- Trustees decrypted whatever the server called the sums, so a dishonest server could have single ballots decrypted. A trustee's browser now fetches every ballot, checks each proof, scope, key, root and nullifier, adds them up itself and decrypts only if that matches the server's sums, once per vote.
- Sending an earlier anonymous ballot again undid a voter's change of mind. A Semaphore ballot now names its hour (message = hour × 8 + option) and counts only in that hour, with five minutes' grace at the turn of the hour; within the hour, a choice the voter changed away from is refused (migration 035). Encrypted ballots can't name an hour, so they're final once cast, and the card says so.
- Encrypted votes took ballots before the trustees had checked their shares, and a complaint, with no evidence, could stop a vote at any time. Ballots now wait until all three checks are in. A complaint is signed and only possible before the first ballot, and the dealer answers it by showing the share, signed, which the server checks against their commitments: a match lets the vote open, anything else stops it and keeps the evidence in the audit file (migration 035). See [docs/votes.md](docs/votes.md#encrypted-weighted-votes-beta).
- A sealed vote's audit file listed its ballots while it was open. It's now ready only once the vote closes.
- Casting an anonymous ballot started with a signed-in fetch of the vote, whose voter list it then proved against, and any root the vote ever had was accepted, which dated the ballot. Browsers now fetch the voter list without the cookie (`GET /api/anonymous-votes/:id`), check it against the roots the server takes ballots for and against the signed-in view, and wait two to ten seconds before sending. A ballot counts only against the current root or one replaced in the last five minutes (migration 035).
- A weighted anonymous vote could be started without trustees, and then never opened. It now needs three valid trustees.
- Vote options must differ, the question and options can't hold control characters or line breaks, and the signed ballot names the option by its number too.
- The weighted signed-vote audit file listed every member's wallets of today. It now lists, with each ballot, the voter's wallets and holdings as read at the snapshot (audit format v2, migration 035), and nobody who didn't vote.
- A smart wallet's ballot is now checked at the block the ballot records, not at whatever block was latest.

### Encryption keys

These changes follow a security review of the encryption. Keys published before this release can't be checked, so migration 023 removes them, together with the old payout and voting key commitments. Everyone sets up their keys again on their next unlock. See [docs/encryption.md](docs/encryption.md) for the trust model.

Nothing opens what was sealed to the old keys. Docs and private tasks encrypted on 3.0.0 stay locked, and private payouts received on 3.0.0 can't be moved from Nil. Before upgrading, download the docs you want to keep, copy out what you need from private tasks, and move private payouts out or copy their keys. [docs/deploy.md](docs/deploy.md) has the steps.

- Signed key directory with pinning. Publishing or resetting encryption keys needs a fresh EIP-4361 statement signed by one of the person's linked wallets, naming the site, the workspace, the account and both public keys. The server checks it, so a stolen session cookie can no longer replace someone's key. Every browser checks the signature again, pins each teammate's keys the first time it sees them, and seals nothing (docs, private-task keys, trustee shares) to a key until its person confirms the fingerprint. Docs shows when someone new appears with a key or someone's key changes, and Settings, Security lists every teammate's key.
- Keys that don't belong to one wallet. Each person's identity is now a random key made in the browser and stored wrapped once per linked wallet, so any linked wallet unlocks it. An optional recovery kit (scrypt and AES-256-GCM, downloaded as a small file) restores it after an admin links a new wallet. A reset also drops the person's copies of private-task keys, so the task's other holder can hand it over again.
- Key messages are bound to the site. Every message a wallet signs for keys has the EIP-4361 layout and names the site from `APP_URL`, so wallets show the domain and warn on other sites. Private payout and voting keys now come from the identity instead of a separate signature that could be replayed. The browser refuses to sign any sign-in, ballot or bounty message from the server that looks like a key message.
- Trustee key setup can't be steered. Trustees of an encrypted vote commit to their dealings before anyone reveals, and each reveal carries a Schnorr proof of knowledge for every commitment, checked by the server and by browsers. Voters rebuild the vote key from the trustees' commitments and refuse a different one from the server. Each trustee's browser checks the shares dealt to it as soon as the key is set up, and the vote takes no ballots until all three have. The audit file carries the commitments and proofs.
- Signed, versioned encrypted content. Doc versions and private-task text are signed with the writer's Ed25519 key, and doc ciphertext is bound to its version number. Content without a valid signature stays locked or read-only, and browsers warn when the server serves an older version of a doc than one they've opened.
- System notifications for private tasks say "A private task" instead of showing the decrypted title.

## 3.0.0 (2026-10-15)

Version 3 makes the Ethereum wallet the only way in and adds NOX token utility: bounties paid on-chain, private payouts, token-weighted and anonymous votes, and an optional NOX subscription. It also adds encrypted docs, everyday tools, sharing, an MCP connection for AI assistants and PowerPoint decks.

### Breaking changes

- Wallet-only sign-in. Email, passwords and passkeys are gone. Sign-In with Ethereum is the only way in. Migration 004 rebuilds the users table without email or password columns and deletes every non-wallet sign-in method. Before upgrading from v2, every person must link an Ethereum wallet. See [docs/deploy.md](docs/deploy.md#11-upgrades).
- Light interface only. Dark mode is removed.

### Added

**Bounties and payouts**

- Bounties on tasks, paid by an admin's own wallet straight to the contributor. The server only reads the chain: it checks the token contract, sender, receiver and amount after enough confirmations, then signs a payment receipt that joins the contributor's proof of work. Pending payments are re-checked every minute.
- A Bounties page: open bounties, amounts promised, owed and paid per person and token, payment history and treasury addresses (for example a Safe multisig) that may also pay.
- Bounties in NOX or USDC. Each task carries its reward token, payments are checked against that token's contract, and totals, receipts, decks, notifications and MCP output show each token separately. `REWARD_TOKENS` configures the list. NOX is always first and USDC on mainnet is the default extra.
- Private payouts to ERC-5564 stealth addresses. Stealth keys come from one deterministic wallet signature and live only in the browser tab. Each payout goes to a fresh one-time address, is announced on the standard announcer and carries a small ETH top-up for gas, in one atomic EIP-5792 batch where the wallet supports it. The server confirms the payout reached the payee's stealth address. Payees can see balances, move funds from the browser or export the key. Derivation matches the ERC-5564 reference SDK on pinned test vectors.
- A public bounty board at `/open`, also published as `/.well-known/nonos-bounties.json`. Outsiders apply by signing a message with their wallet, with no account or email. Accepted applicants become guests who see only their task.

**Votes and membership**

- Votes signed by the voter's wallet, counted one per person or by voting power. Results can be sealed until the vote closes. Admins can download a recount file.
- A token-holder door: admins can let anyone holding a minimum of NOX join as a member. For people who joined that way, the balance is checked again at every sign-in.
- Voting power = NOX in linked wallets + NOX staked in the official staking contract + Zero-State Passes × a power per ZSP that admins set (`VOTE_ZSP_POWER` is the default). It is read for every member at one block when a weighted vote opens, so tokens moved during the vote can't count twice and people who join later have no power in it. The recount file carries the block, the contracts and every member's breakdown.
- Anonymous votes with Semaphore zero-knowledge proofs. Each member's voting key is derived from a wallet signature, and only its public commitment reaches the server. Ballots are proven in the browser from circuit files the server hosts, sent without the session cookie, and limited to one per member per vote. The recount file holds every root and proof but no names. `npm run zk:fetch` downloads circuit files for other tree depths and keeps them only if they pass hash and proof checks.
- Beta: encrypted weighted anonymous votes with three trustees. A new circuit (`circuits/ballot.circom`, 30,669 constraints) proves the voter is in the vote's census with their snapshotted power and encrypts that power into the chosen option with exponential ElGamal on Baby Jubjub. Trustees run a distributed key generation, so nobody holds the private key. After the vote closes, any two trustees decrypt only the totals, with Chaum-Pedersen proofs. The circuit has not been audited, and its Groth16 phase 2, recorded in `circuits/CEREMONY.json`, is a development ceremony run on one machine. It must be rerun with independent contributors before these votes are relied on. `npm run zk:ballot` rebuilds the circuit and setup.

**Subscription**

- An optional NOX subscription. A workspace pays NOX from an admin's wallet or a treasury address to the operator's treasury, and the server adds one period per full price after checking the transfer on-chain. Nothing is charged automatically.
- Paid tools: new bounties and public listings, opening new votes, the token-holder door, built-in AI, the MCP connection, and teams beyond the free seats. Reading, exporting, paying bounties already promised and finishing votes already opened (ballots, closing and trustee decryption) are never gated.
- A free trial counted from workspace setup, a grace period after a lapse, and community mode (everything unlocked) when `PLAN_TREASURY` is not set.
- Settings → Plan: status, price, seats, paying 30 to 360 days from a wallet or by pasting a multisig transaction, and payment history.

**Everyday work**

- Private tasks, visible only to their creator and assignee, not even to admins.
- Personal time tracking with a timer, a private timesheet and CSV export.
- Reminders that arrive as notifications.
- An installable progressive web app. Its service worker never caches API data.

**Docs, sharing and AI**

- End-to-end encrypted docs. Keys are derived in the browser from a deterministic wallet signature over a message that names the workspace by its signing key, so renaming the workspace doesn't change anyone's keys. Private payout and voting keys work the same way. Every doc has its own AES-256-GCM key sealed per reader. The server stores only ciphertext, keeps 25 encrypted revisions, refuses stale saves and re-keys a doc when a reader is removed. Online teammates hand team docs to newcomers automatically.
- Project guests, member invites (when admins allow them) and read-only share links. Share links are off until an admin enables them, stored as hashes, expiring and revocable, and show no people, comments, files, addresses or private tasks.
- An MCP endpoint at `/mcp` for AI assistants, authenticated by personal access keys that are shown once, stored as hashes, scoped read or read-write, expiring and revocable. Eight tools run through the same visibility rules as the app.
- Draft with AI in docs, with a plain notice of what leaves the browser.
- One-click PowerPoint status decks for the workspace, a project or a goal, built in the browser, with speaker notes. With AI on, Claude can write the summary and notes from the facts on the slides.

### Changed

### Security

- Patched security advisories in express, ws and vite. Transitive ws, snarkjs and underscore are pinned to patched versions.
- Docker builds leave out local data folders, databases, capsules, exports, `.env` files and keys wherever they sit in the tree, and the Dockerfile removes any that slip into the server folder before the runtime image is assembled.

### Known limits

- No part of NØNOS's own code has had an independent security audit.
- Encrypted weighted votes are beta, for the reasons above.
- See [Honest limits](docs/privacy-model.md#honest-limits) in the privacy model.
